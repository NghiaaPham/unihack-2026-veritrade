# VeriTrade

Verifiable trade settlement on Avalanche. pnpm + Turborepo monorepo.

## Stack

| Layer     | Technology                               |
| --------- | ---------------------------------------- |
| Web       | Next.js 16 (App Router) + React 19       |
| API       | NestJS 12                                |
| Contracts | Solidity 0.8.28 + Hardhat 3 (viem)       |
| Database  | PostgreSQL 17 + Prisma 7                 |
| Chain     | Avalanche Fuji Testnet (C-Chain, 43113)  |
| Tooling   | TypeScript 6, ESLint 10, Prettier, Turbo |

## Layout

```
apps/
  web/                 Next.js client            -> :3000
  api/                 NestJS HTTP API           -> :3001
packages/
  config/              Shared tsconfig presets (no build step)
  contracts/           Hardhat project, Fuji network, deploy script
docs/
  architecture.md      module boundaries, request lifecycle, health design
  database-design.md   models, indexes, state machines, duplicate-financing threat model
  security-assumptions.md  trust boundaries, what may go on-chain, known gaps
  development-setup.md     install, migrate, seed, test, troubleshooting
  blockchain-architecture.md    BlockchainModule, the outbox, what each service owns
  invoice-commitment-spec.md    the versioned on-chain commitment and its privacy analysis
  financing-state-machine.md    chain states, database states and how they relate
  avalanche-fuji-deployment.md  deploy, roles, verification, the guards that block mistakes
  blockchain-security.md        roles, trust assumptions, admin powers, what is not defended
  transaction-reconciliation.md unknown outcomes, retries, reorgs, the indexer
```

### Why this shape

- **`apps/` holds deployables, `packages/` holds shared libraries.** `contracts` lives
  under `packages/` because its output (ABIs, addresses) is consumed by `apps/`, not
  deployed as a service. It still exposes a `build` task, so Turbo builds it first
  whenever a consumer declares `dependsOn: ["^build"]`.
- **One tsconfig per target, not per app.** `packages/config` ships three presets —
  `nextjs` (bundler resolution, `jsx: preserve`), `nestjs` (NodeNext, decorator
  metadata), `node` (NodeNext, for scripts). Apps extend them by package name, so
  compiler settings change in one place. The package has no build step: TypeScript
  resolves the JSON directly.
- **Workspace packages are consumed as source.** `@veritrade/config` and
  `@veritrade/contracts` are linked with `workspace:*`. No `dist` indirection until a
  package actually needs to publish.
- **Health endpoints are split by question, not by prefix.** `/api/v1/health` is liveness
  and touches nothing external; `/api/v1/health/db` is readiness and runs a real
  `SELECT 1`. Conflating them means a slow database restarts healthy instances. `/health`
  stays unversioned at the root for container probes, and `/api/health` deliberately
  stays a `404`.
- **Prisma 7 over a driver adapter, not over the bundled engine.** Prisma 7 is
  Rust-free: it talks SQL through `@prisma/adapter-pg`, which borrows an ordinary `pg`
  pool. One pool per process, one shutdown path, and no engine binary to download. The
  generated client is TypeScript emitted into `apps/api/src/generated/` (git-ignored) and
  is regenerated by `postinstall` and `prebuild`.
- **Migrations are generated without a database.** `prisma migrate diff` reads the schema
  file and emits SQL, so the migration is a reviewable artifact produced on a machine
  with no Postgres running. See [docs/database-design.md](docs/database-design.md).
- **The data layer lives in `apps/api`, not a shared package.** Only the API talks to
  Postgres today. Lifting `src/database` into `packages/db` is a mechanical move once a
  second consumer appears; doing it now would be premature.

## Getting started

```bash
pnpm install

# environment
cp .env.example .env                        # postgres creds for docker-compose
cp apps/api/.env.example apps/api/.env
cp apps/web/.env.example apps/web/.env
cp packages/contracts/.env.example packages/contracts/.env

pnpm db:up                                 # postgres via docker compose
pnpm db:migrate                            # apply schema
pnpm db:seed                               # synthetic development data
pnpm dev                                   # web :3000, api :3001
```

Docker is optional for development: the API test suite runs against PGlite and needs no
server. You need it only for `db:migrate`, `db:seed` and `db:studio`.

Contracts:

```bash
pnpm --filter @veritrade/contracts compile
pnpm --filter @veritrade/contracts test        # 33 tests against a local EVM
pnpm --filter @veritrade/contracts env:check   # read-only pre-flight, no transaction
pnpm --filter @veritrade/contracts deploy:local

```

`deploy:fuji` refuses unless `CONFIRM_DEPLOY` is exactly `fuji:43113`. That is
deliberate friction, not a bug: the value names both the network and the chain id the
node actually reports, so a misconfigured `FUJI_RPC_URL` pointing somewhere else fails
the check instead of deploying. Mainnet (43114) has a dedicated refusal. No script ever
prints a private key — `env:check` prints the RPC _host_ and whether a key is present,
nothing more.

## Database and migrations

Schema: `apps/api/prisma/schema.prisma`. Migrations: `apps/api/prisma/migrations/*/migration.sql`,
committed and reviewed like code. `prisma migrate diff` reads the schema file and emits
SQL, so a migration can be authored and reviewed with no database running.

```bash
cd apps/api
prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script \
  -o prisma/migrations/<timestamp>_name/migration.sql

pnpm db:generate                          # regenerate the client (no database needed)
pnpm db:validate                          # parse and validate the schema
pnpm db:migrate                           # apply committed migrations (needs Postgres)
pnpm --filter @veritrade/api db:studio    # browse data
```

Workflow: change `schema.prisma` → `migrate diff` → read the SQL → commit it →
`db:migrate`. Never edit an applied migration; add a new one.

`PrismaService` (`apps/api/src/database/prisma.service.ts`) owns a `pg` pool, hands it to
`PrismaPg`, and is exported globally from `PrismaModule`. The pool connects lazily: the
API boots and serves `/api/v1/health` even when Postgres is down, and the failure
surfaces on the first query — or on `/api/v1/health/db`, which exists to make it
observable. A missing or malformed `DATABASE_URL` is the exception: it fails fast at boot
via `config/env.validation.ts`.

Sixteen tables: eleven across the domain modules, the three Phase 4 chain
records (`blockchain_operations`, `blockchain_transaction_receipts`,
`blockchain_events`), and the two Phase 1 records (`chain_sync_cursor`, `trade`). The
models, their relations, the indexes that back them, the state machines, and the
duplicate-financing threat model are documented in
[docs/database-design.md](docs/database-design.md). The outbox and why it exists are in
[docs/transaction-reconciliation.md](docs/transaction-reconciliation.md).

Two things worth knowing before you query:

- `Organization` is the tenant root; every tenant-owned row carries `organization_id` and
  every composite index leads with it.
- `financing_requests.active_key` is `'ACTIVE'` while a request is live and `NULL` once it
  is terminal. Postgres treats `NULL`s as distinct in a unique index, so
  `@@unique([invoiceId, activeKey])` permits exactly one live request per invoice while
  allowing any number of rejected or cancelled ones.

## Trade API

| Method | Path                                 | Behaviour                                          |
| ------ | ------------------------------------ | -------------------------------------------------- |
| `POST` | `/api/trades`                        | `201` with the row; `409` on duplicate `reference` |
| `GET`  | `/api/trades?status=&limit=&offset=` | `{ data, total }`; `limit` 1–100, default 20       |
| `GET`  | `/api/trades/:id`                    | `200`, or `404` when missing                       |

Validation runs through a global `ValidationPipe` with `whitelist` and
`forbidNonWhitelisted`, so an unknown field is a `400` rather than being silently
dropped. Input rules: `reference` ≤ 64 chars, both addresses `0x` + 40 hex, `amount` a
positive decimal string with ≤ 18 fraction digits, `chainId` optional (defaults to
43113). Addresses are lowercased before insert so the checksummed and unchecksummed
forms cannot become separate rows. `amount` is returned as a string — it is never
parsed into a float.

`status` is not settable on create; it defaults to `draft`. Settlement transitions are
not implemented yet.

> The trade endpoints predate the auth layer and are **unauthenticated**. They are kept
> so the Phase 1 regression suite keeps running. Use the invoice API below.

## Invoice API

Nine endpoints under `/api/v1/invoices`: the seven below, plus `POST /:id/anchor` and
`GET /:id/anchor-status`, which are described with the rest of the chain surface in the
next section. All require `Authorization: Bearer <token>` from
`POST /api/v1/auth/register` or `/login`, and all are scoped to the organisation in that
token — no request parameter can override it.

| Method | Path                | Behaviour                                                                                                                         |
| ------ | ------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `POST` | `/`                 | `201` from structured metadata; `409` on a duplicate or conflicting identity                                                      |
| `POST` | `/upload`           | `201` from an XML document (multipart, field `file`); `413`, `422`                                                                |
| `GET`  | `/`                 | `{ items, pagination }`; filters `status`, `issuerTaxId`, `invoiceNumber`, `from`, `to`; sorts `createdAt`, `issueDate`, `amount` |
| `GET`  | `/:id`              | `200` with the latest verification, `404` for another tenant's id                                                                 |
| `GET`  | `/:id/verification` | Latest run, or `null` when none has completed                                                                                     |
| `GET`  | `/:id/history`      | Every run plus the audit events, newest first                                                                                     |
| `POST` | `/:id/verify`       | Re-runs verification, appending a new run                                                                                         |

OpenAPI is served at `/api/docs` outside production.

Two things the API is careful about:

- **Identity is not content.** The fingerprint covers seller tax id, series, number and
  template code. Amounts, buyer and dates are a separate content hash. A re-issued
  invoice with a corrected amount therefore surfaces as a _conflict_ rather than as a new
  document.
- **Verification is local only.** Every result carries `scope: LOCAL_CHECKS_ONLY`.
  Signature trust chains and tax-authority approval are reported as `NOT_CHECKED` and
  `UNSUPPORTED`, so no invoice can reach `PASSED` today. That is deliberate — see
  [docs/invoice-verification.md](docs/invoice-verification.md).

Processing rules, supported XML formats and the normalisation table are in
[docs/invoice-processing.md](docs/invoice-processing.md). The parsing threat model and
the storage requirements for production are in
[docs/invoice-security.md](docs/invoice-security.md).

## Blockchain API

Six routes on the invoice and financing resources, plus one read-only transaction
lookup. Same bearer token, same tenant scoping.

| Method | Path                                                | Behaviour                                                          |
| ------ | --------------------------------------------------- | ------------------------------------------------------------------ |
| `POST` | `/api/v1/invoices/:id/anchor`                       | `200` confirmed, `202` pending, `409` rejected; idempotent         |
| `GET`  | `/api/v1/invoices/:id/anchor-status`                | Operation state plus the live `claimStatus` read from the contract |
| `POST` | `/api/v1/financing-requests/:id/reserve`            | `RESERVED`; no new transaction if the invoice is already anchored  |
| `POST` | `/api/v1/financing-requests/:id/declare-financed`   | `FINANCING_DECLARED`; an attestation, not a disbursement           |
| `POST` | `/api/v1/financing-requests/:id/close`              | `CLOSED`, terminal on chain                                        |
| `POST` | `/api/v1/financing-requests/:id/cancel-reservation` | Releases a `RESERVED` claim; never touches a financed one          |
| `GET`  | `/api/v1/blockchain/transactions/:id`               | The operation, its receipt, and the block it landed in             |

Every write returns the operation, so a `202` tells the client exactly what to poll.
The three possible answers are deliberate: `200` means the receipt is in and the
business row has been updated; `202` means either the transaction is mined but not yet
past the confirmation depth, or its outcome is genuinely unknown (the RPC timed out
after the transaction may have been broadcast). `409` means the contract rejected it,
and the error name is carried through — `ClaimAlreadyActive`, `NotReserved`,
`NotFinanced` — rather than flattened into a generic failure.

Three things this layer refuses to do:

- **Claim that a payment happened.** `declare-financed` records that a financier
  attested to an agreement. The contract cannot see a bank transfer and neither can the
  API, so the database moves to `FINANCING_DECLARED`. `FUNDED` exists in the schema and
  nothing writes it.
- **Sign for the caller.** No endpoint accepts a key, a raw transaction, or a
  destination. The server holds one signer; the API decides which of four contract calls
  to make from the route and the row it loaded.
- **Resend on a timeout.** A timeout is recorded as `UNKNOWN` with the signed hash kept.
  Reconciliation looks the hash up; it never re-signs. See
  [docs/transaction-reconciliation.md](docs/transaction-reconciliation.md).

The commitment is not the Phase 3 fingerprint. It is `keccak256(abi.encode(domain,
schemaVersion, identityDigest))`, so the on-chain value cannot be recomputed from a
guessed invoice number without also knowing the domain string and schema version — and
even then the result is opaque. [docs/invoice-commitment-spec.md](docs/invoice-commitment-spec.md)
works through the dictionary-attack analysis and why cross-organisation duplicate
detection still holds.

## Testing

`apps/api` runs Vitest. The suite boots the real `AppModule` through
`@nestjs/testing` and overrides only `PrismaService`, so routing, the validation pipe,
exception mapping, DI wiring and every query run for real.

The database is PGlite — Postgres compiled to WASM — with the committed migrations
applied at startup, exposed over the Postgres wire protocol so Prisma reaches it through
the ordinary `pg` adapter. The tests therefore exercise the actual DDL, including the
unique constraints behind the `409` response.

```bash
pnpm test                                  # all workspaces
pnpm --filter @veritrade/api test          # one workspace
pnpm --filter @veritrade/api test:watch
```

197 tests across thirteen files:

| File                            | Covers                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `invoice-api.e2e-spec.ts`       | The seven endpoints: intake, upload, duplicates, tenant isolation, pagination, history, storage failure |
| `invoice-xml-parser.spec.ts`    | Profiles, XXE/DTD rejection, UTF-8 strictness, depth and node limits, unsupported formats               |
| `verification-checks.spec.ts`   | Each check's pass, fail, skip and unsupported paths                                                     |
| `verification-engine.spec.ts`   | Aggregation rules, a throwing check, no driver text in the stored result                                |
| `invoice-fingerprint.spec.ts`   | Determinism, identity sensitivity, incomplete identity, content versus identity                         |
| `trade.e2e-spec.ts`             | The Phase 1 trade API, unchanged, now running on Prisma                                                 |
| `schema.spec.ts`                | Tenant-scoped duplicate detection, single-active-financing, FK rules, 38-digit decimal round trip       |
| `health.e2e-spec.ts`            | Liveness, readiness, `503` on an unreachable database, no error leak                                    |
| `domain-modules.spec.ts`        | All eight domain services resolve from the root container                                               |
| `pg-interop.spec.ts`            | The built output links under Node's ESM loader; `pg` still exports `Pool`                               |
| `seed-compat.spec.ts`           | The modules the seed imports load under Node's type stripping, and hash identically to the service      |
| `blockchain-commitment.spec.ts` | The golden commitment vector, domain separation, ABI drift against the compiled artifact, RPC guards    |
| `blockchain.e2e-spec.ts`        | Anchor, idempotency, cross-org collision, full lifecycle, cancellation, indexer replay and a real reorg |

`blockchain.e2e-spec.ts` is the only test that starts a second process: it runs
`hardhat node` on port 8546, deploys the compiled contract, grants both roles, and then
sets the chain environment before importing `AppModule`. That ordering is not
cosmetic — `ConfigModule.forRoot({ validate })` runs when the module is evaluated, so a
static import would freeze the chain id before the test could set it.

The contracts package has its own suite, 33 tests over the same contract:

```bash
pnpm --filter @veritrade/contracts test        # hardhat test (node:test)
pnpm --filter @veritrade/contracts typecheck   # compile, then tsc
```

It covers the fourteen scenarios in the specification plus a randomised invariant test:
240 deterministic operations against a six-commitment model, asserting after _every_
step that `statusOf` and `isActive` agree with the model and that each accepted
transition emitted exactly one event.

TypeScript is compiled through SWC (`unplugin-swc`), not esbuild: Nest's DI reads
`design:paramtypes` metadata, which esbuild cannot emit. Tests are typechecked by
`tsconfig.spec.json` (it adds `vitest/globals`, the `test/` directory and `prisma/`); the
build config does not see them.

## Health checks

| Endpoint                               | Question                  | Database   | Failure |
| -------------------------------------- | ------------------------- | ---------- | ------- |
| `GET /api/v1/health`                   | Is the process alive?     | No         | —       |
| `GET /api/v1/health/db`                | Can it reach PostgreSQL?  | `SELECT 1` | `503`   |
| `GET /health`                          | Legacy alias for liveness | No         | —       |
| `GET http://localhost:3000/api/health` | Web app liveness          | No         | —       |

Liveness returns `status`, `service`, `environment`, `uptimeSeconds` and `timestamp`.
Readiness adds `database: { connected, latencyMs }`. On failure it returns `503` with
`{ connected: false, error: 'database unreachable' }` — the driver's message is logged,
never returned, because Prisma connection errors can echo the connection string.

`/health` stays at the root because container probes are pointed at it. `/api/health` is
not a route and returns `404`; a test asserts that.

## Environment

Every variable is documented in a committed `.env.example`; real `.env` files are
git-ignored. Only `NEXT_PUBLIC_*` values reach the browser — never put a private key or
database URL behind that prefix. `DEPLOYER_PRIVATE_KEY` belongs to `packages/contracts`
only.

## Module format

`apps/api` is ESM (`"type": "module"`, `module: NodeNext`). Every `@nestjs/*` package in
v12 is ESM-only, so a CommonJS build only ran by leaning on Node's `require(esm)` and
would have failed on Node 20.

The one rule this imposes: **relative imports need a `.js` extension**. TypeScript does
not rewrite specifiers, so `./app.module` must be written `./app.module.js` even though
the file on disk is `app.module.ts`.

The single exception is Prisma's generated client, which imports its own files with
explicit `.ts` specifiers. `tsconfig.nestjs.json` sets `rewriteRelativeImportExtensions`,
so TypeScript rewrites those to `.js` on emit and the built output is valid Node ESM.
Hand-written code must not use `.ts` specifiers.

`apps/web` and `packages/contracts` are unaffected.

## Deliberately not included yet

Phase 4 added the Avalanche registry, the outbox and the lifecycle endpoints. The HTTP
surface is now the health endpoints, the legacy trade endpoints, `POST /api/v1/auth/*`,
the nine invoice endpoints, the four financing-request routes, and
`GET /api/v1/blockchain/transactions/:id`.

Deferred, and honestly so:

- **No Fuji deployment.** The contract compiles, the scripts work against a local EVM,
  and the Fuji guards fire — but no transaction has been sent to 43113. There is no
  deployer key in this repository and none was generated. Everything below the RPC
  boundary is proven; the deployment itself is not.
- **No automated reconciler.** `UNKNOWN` operations are reconciled when a client polls
  them. A worker that sweeps stale operations on a timer is not written, so an operation
  whose client disappears stays `UNKNOWN` until someone looks.
- **The indexer is a single-instance poller.** It is restart-safe and handles a reorg by
  rewinding one block per pass, but two API instances both polling would race on the
  same cursor. A real deployment needs a lease or a separate indexer process.
- **Tax-authority verification.** No authorised integration exists, so the check reports
  `UNSUPPORTED` on every run rather than pretending. `PASSED` is therefore unreachable
  by design, which means anchoring requires a `PARTIAL` result — the API says so in the
  `409` body.
- **Certificate trust chains.** No CA trust store and no OCSP/CRL source.
- **Actual disbursement.** `declare-financed` is an attestation. No endpoint moves money
  and the contract holds no funds.
- **Production document storage.** `LocalDocumentStorage` is a development
  implementation; [docs/invoice-security.md](docs/invoice-security.md) lists what an
  object-store implementation must provide.
- **Rate limiting, CI workflows, an ABI-driven API client.**
- **Docker on this machine.** `docker-compose.yml` is correct, but Docker is not
  installed here, so migrations were never applied to a server-backed Postgres. Every
  test runs against PGlite over the wire protocol — real Postgres SQL, not a real
  Postgres server. See [docs/development-setup.md](docs/development-setup.md).
